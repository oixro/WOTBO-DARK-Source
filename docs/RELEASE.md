# Публикация обновления

Автообновление WOTBO **не использует GitHub Releases**. 2.33+ читают три файла
с ветки `main` публичного репозитория `oixro/WOTBO`:

- `WOTBO.exe` — новый бинарник;
- `ver.json` — версия, например `2.34.0`;
- `lastchange.json` — текст «Что нового» (это не JSON, а обычный текст).

Приложение сравнивает `AssemblyVersion` запущенного exe с `ver.json`.
Если remote больше — предлагает обновление, качает `WOTBO.exe` из `main`
и перезапускается.

## Чеклист

1. Поднять версию в `Properties/AssemblyInfo.cs`:
   - `AssemblyVersion("2.34.1.0")`
   - `AssemblyFileVersion("2.34.1.0")`
2. Добавить раздел в `CHANGELOG.md` с той же версией в заголовке:
   `## 2.34.1 — 2026-11-22`. Скрипт берёт первый раздел как «Что нового».
3. Проверить сборку и приложение на VM:
   - окно запускается, версия в правом нижнем углу читается;
   - твики применяются;
   - нет ошибок в `%TEMP%\wotbo.log`.
4. Закоммитить изменения в `WOTBO-DARK-Source`.
5. Запустить публикацию:
   ```bash
   export WOTBO_VM_SSH=wotbo-vm
   ./build/release-public.sh
   ```
6. Проверить, что файлы обновились (raw может кэшироваться несколько минут):
   ```bash
   curl -s https://raw.githubusercontent.com/oixro/WOTBO/main/ver.json
   curl -sI https://raw.githubusercontent.com/oixro/WOTBO/main/WOTBO.exe
   ```
7. Проверить обновление «с улицы»: на VM поставить предыдущую версию,
   запустить, дождаться предложения обновиться, согласиться, убедиться,
   что после перезапуска версия новая и обновление больше не предлагается.

## Скрипт

```bash
./build/release-public.sh              # сборка + публикация
./build/release-public.sh --no-build   # публикация готового artifacts/x64/Release/WOTBO.exe
./build/release-public.sh --dry-run    # проверки + локальные коммиты, без push
./build/release-public.sh --notes FILE # свой текст для lastchange.json
./build/release-public.sh --allow-dirty
```

Что проверяет:

- `AssemblyVersion` из `AssemblyInfo.cs` читается и совпадает с версией
  собранного exe (через VM);
- exe существует и больше 100 КБ;
- публичный `ver.json` **меньше** новой версии — иначе скрипт остановится,
  чтобы не гонять одно и то же обновление;
- первый раздел `CHANGELOG.md` относится к публикуемой версии (иначе
  используй `--notes`);
- в git нет незакоммиченных изменений (если не передан `--allow-dirty`).

Порядок публикации:

1. `WOTBO.exe`
2. `ver.json`
3. `lastchange.json`

Менять порядок нельзя: если сначала обновить `ver.json`, пользователи
скачают старый exe, версия останется прежней, и обновление зациклится.

## Версии

- Патч/фикс: `2.34.1`, `2.34.2`, …
- Новая функциональность: `2.35.0`.
- `2.34` и `2.34.0.0` для апдейтера одно и то же (версия дополняется нулями),
  в `ver.json` пишется короткая версия: `2.34.0`.
- В окне показывается короткая версия без «build»: `2.34`, `2.34.1`,
  `2.34.1.5`. В dev-режиме (локальная версия новее публичной) добавляется
  ` dev`.

## Если что-то пошло не так

- **Опубликовали старый exe с новой версией.** Пользователи обновятся на
  старую сборку и снова увидят предложение. Исправление: залить правильный
  `WOTBO.exe`, затем снова `ver.json` (тот же номер) — сравнение по версии
  не изменится, но те, кто ещё не обновился, получат правильный файл.
- **Нужно откатить версию.** Верни предыдущий `ver.json`. У уже обновившихся
  remote станет меньше local — приложение покажет `dev` и не будет
  откатываться само.
- **GitHub Release.** Тег и релиз можно делать для истории, но на
  автообновление они не влияют. Ассеты релиза никто не читает.
